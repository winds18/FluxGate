# 开发规范

## 1. 总原则

FluxGate 的开发节奏采用“由大到小，层层推进”的方式：

```text
项目目标
-> 阶段目标
-> 功能模块
-> 可验收任务
-> 代码实现
-> 自动化测试
-> 文档同步
-> 提交和推送
```

任何开发任务都必须先计划，再实现。不能直接进入编码。

## 2. 标准开发流程

每次开发必须按以下顺序执行：

1. 理解需求和当前代码状态。
2. 制定计划，明确本轮边界。
3. 拆分子任务。
4. 编排协作角色。
5. 实现代码。
6. 运行验收测试。
7. 测试完全通过后同步文档。
8. 检查 Git 变更范围。
9. 提交代码。
10. 推送远程仓库。

如果验收测试未完全通过，不进入文档同步、提交和推送阶段。

## 3. 脚本化规范

开发过程中能用脚本管理的动作，必须沉淀为脚本。

必须脚本化的动作：

## 4. Shell 使用限制

临散 shell 命令只能用于读操作。

允许的临散 shell 操作：

- `pwd`
- `ls`
- `find`
- `rg`
- `sed -n`
- `git status`
- `git diff`
- `git log`
- `go test` 等纯执行型验证命令
- `docker ps` 等状态查询命令
- `docker compose ps` 等状态查询命令
- 查看日志的只读命令

禁止的临散 shell 写操作：

- `cat > file`
- `echo ... > file`
- `tee file`
- `mkdir`
- `rm`
- `mv`
- `cp`
- `touch`
- `chmod`
- `docker compose up -d` 这类会改变运行状态的命令
- 任何直接写入、删除、移动、部署、重启的命令

写操作必须通过以下方式之一完成：

- 已纳入版本管理的脚本。
- `apply_patch` 修改源码和文档。
- 项目正式提供的 CLI。

在脚本尚不存在时，先创建脚本文档或脚本文件，再通过脚本执行对应动作。

## 5. 协作角色编排

每次开发前，需要根据任务规模明确角色。

常用角色：

- Planner：梳理需求、拆任务、定义验收标准。
- Architect：检查架构边界、数据流、接口契约。
- Backend：实现 Go API、服务层、数据库访问。
- Frontend：实现管理后台 UI。
- Data Plane：实现 sing-box 配置生成、统计采集、发布流程。
- QA：设计并执行测试、验收边界和回归检查。
- Observability：确保日志、指标、诊断信息和截图证据可追踪。
- Docs：同步 README、设计文档、部署文档和变更说明。
- Release：检查 Git 状态、分支、提交、推送和部署准备。

任务简单时可以由一个人承担多个角色，但计划中必须明确这些职责是否覆盖。

任务复杂时可以并行拆分，但必须保证不同子任务的文件写入范围尽量不重叠。

## 6. 分支策略

分支设计要保持清晰、可靠、可回滚。

长期分支：

```text
main
```

规则：

- `main` 始终保持可构建、可部署。
- 不直接在 `main` 上做大功能开发。
- 所有功能通过短生命周期分支合入。

开发分支命名：

```text
codex/phase-0-docs
codex/feature-token-management
codex/feature-sing-box-config
codex/feature-traffic-stats
codex/fix-config-rollback
codex/docs-deployment
```

分支类型：

- `codex/phase-*`：阶段性推进。
- `codex/feature-*`：功能开发。
- `codex/fix-*`：缺陷修复。
- `codex/docs-*`：纯文档调整。
- `codex/chore-*`：构建、脚本、依赖、维护工作。

提交原则：

- 一个提交只表达一个清晰主题。
- 提交前必须确认没有夹带无关文件。
- 不提交 `.env`、数据库文件、日志、备份和本地构建产物。
- 涉及行为变化时，必须同步对应文档。

## 7. 开发节奏

采用大阶段推进：

```text
Phase 0: 文档和技术验证
Phase 1: MVP 控制面
Phase 2: 真实流量统计和额度
Phase 3: 上游订阅自动同步
Phase 4: 节点探针和路由优化
Phase 5: 运维增强
```

每个阶段内部继续拆成小任务：

```text
设计
-> 数据模型
-> API
-> 前端
-> 脚本
-> 测试
-> 文档
-> 提交
```

每个小任务必须能独立验收。

## 8. 验收测试规范

开发完成后必须执行验收测试。

最小验收层级：

- 单元测试
- 集成测试
- 配置生成测试
- 数据库 migration 测试
- API 测试
- 前端构建测试
- Dockerfile 和 compose 静态验证
- 远程镜像构建测试
- sing-box 配置 `check`
- 页面截图或视觉验收

涉及部署时追加：

- 远程环境探测
- 磁盘水位检查
- 远程镜像拉取或构建验证
- Docker Compose 启动验证
- 健康检查
- 订阅接口验证
- 测试用户连接验证
- 流量统计采集验证
- 禁用/过期/超额阻断验证
- 部署诊断日志归档

涉及管理后台页面时：

- 自行启动或访问测试环境。
- 自行截图关键页面。
- 检查页面是否空白、错位、遮挡、溢出。
- 检查核心操作流是否可点击、可提交、可反馈。
- 最终说明中提供截图路径或截图结论。

验收结果必须在最终说明中写清楚：

- 执行了哪些测试。
- 哪些通过。
- 哪些未执行。
- 未执行的原因。
- 残余风险。

## 9. 文档同步规范

只有测试完全通过后，才进入文档同步阶段。

必须同步的文档：

- README
- 架构文档
- 数据模型文档
- API 文档
- 部署文档
- Roadmap
- 审阅清单或决策记录

文档要说明：

- 新增能力。
- 行为变化。
- 配置变化。
- 部署变化。
- 运维影响。

## 10. 自动化唤醒机制

当任务很多、执行时间长、需要持续推进时，使用自动化唤醒机制。

规则：

- 长任务开始前明确唤醒目标。
- 默认每分钟唤醒一次。
- 每次唤醒检查当前阶段、阻塞点、测试结果和下一步动作。
- 唤醒只用于推进任务，不替代验收。
- 任务完成后关闭对应自动化唤醒。

适用场景：

- 长时间测试。
- 远程部署观察。
- CI 等待。
- 多阶段重构。
- 大批量文档或代码同步。

## 11. 自闭环开发原则

开发过程默认由 Codex 自主推进闭环，尽量不打扰用户。

应该自行处理：

- 查阅代码和文档。
- 制定计划。
- 拆分任务。
- 编排角色职责。
- 编写或复用脚本。
- 本地验证。
- 远程构建。
- 远程部署。
- 日志采集。
- 页面截图。
- 验收测试。
- 文档同步。
- 提交和推送。

只有出现以下情况才打扰用户：

- 需要用户提供密钥、账号、域名、证书等敏感信息。
- 需要对生产数据执行不可逆操作。
- 需要确认费用、资源购买或服务器变更。
- 需求本身存在互相冲突。
- 自动化验收发现高风险问题，需要用户决策。

## 12. 可观测开发要求

所有脚本和服务都要为后续调试保留清晰日志。

要求：

- 每个脚本输出开始时间、结束时间、执行参数摘要和结果。
- 每次部署生成 `deploy_id`。
- 每次配置发布生成 `config_version`。
- 服务日志包含 request id。
- 订阅请求、配置发布、统计采集、Token 状态变化必须有结构化日志。
- 失败时自动收集诊断信息。
- 页面验收时保存截图或记录截图检查结论。

日志目录规划：

```text
logs/
├── deploy/
├── fluxgate/
├── sing-box/
├── qa/
└── diagnostics/
```

## 13. 远程仓库同步

远程仓库：

```text
git@github.com:winds18/FluxGate.git
```

同步顺序：

```text
git status
-> 确认变更范围
-> 运行测试
-> 同步文档
-> 再次 git status
-> git add
-> git commit
-> git push
```

提交和推送只能在验收通过后进行。

## 14. 禁止事项

禁止：

- 未计划直接编码。
- 未验收直接提交。
- 测试失败后同步发布。
- 临散 shell 写文件。
- 临散 shell 删除文件。
- 手动散落执行部署写操作。
- 没有环境探测直接远程部署。
- 磁盘 critical 时强行部署。
- 没有保存日志的远程构建或部署。
- 将敏感配置提交到仓库。
- 将旁边项目或无关文件带入提交。
- 在未确认的情况下重置或覆盖用户已有改动。

## 15. 每轮开发检查表

开发前：

- [ ] 已理解需求。
- [ ] 已查看当前代码和 Git 状态。
- [ ] 已制定计划。
- [ ] 已拆分子任务。
- [ ] 已明确协作角色。
- [ ] 已确认需要新增或复用哪些脚本。
- [ ] 已确认是否需要远程构建或远程部署。
- [ ] 已确认是否需要页面截图验收。

开发中：

- [ ] 写操作通过脚本、项目 CLI 或 `apply_patch` 完成。
- [ ] 临散 shell 只做读操作。
- [ ] 子任务边界清晰。
- [ ] 无关文件未被修改。
- [ ] 日志和诊断信息可追踪。

开发后：

- [ ] 测试完全通过。
- [ ] 页面相关变更已截图或视觉验收。
- [ ] 文档已同步。
- [ ] Git 变更范围已复核。
- [ ] 提交信息清晰。
- [ ] 已推送远程仓库。
- [ ] 已说明验收结果和残余风险。
